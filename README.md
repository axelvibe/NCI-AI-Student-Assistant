# NCI Student Information Assistant

A small, dependency-free chatbot that answers **NCI student** questions using a
curated knowledge base, a registry of official NCI pages, and a grounded AI answer
generated by a Google Apps Script proxy.

It is a plain static site: `index.html`, `style.css`, `app.js`, `knowledge.json` and
`sources.json`. No build step and no framework. The OpenAI key never touches the
repository; it lives in Apps Script.

## The one rule

**Answers are grounded in `knowledge.json` and official NCI pages, and every answer
links to the official page(s) it used.** When there is not enough verified content
the assistant says so, points the student to the NCI Support Hub, and — if the
question is off-topic — declines. It never invents a date, fee, deadline or URL.

## Files

| File | Purpose |
| --- | --- |
| `index.html` | Page structure and the chat UI |
| `style.css` | Styling, responsive down to phone widths |
| `app.js` | Source selection, grounded AI calls, chat UI, survey, anonymous beacons |
| `knowledge.json` | Curated answers used as the primary grounding layer |
| `sources.json` | Registry of official NCI pages and allowed link hosts |
| `docs/google-apps-script/Proxy.gs` | Apps Script proxy: AI answers, logging and reports |
| `docs/REPORTING.md` | Data dictionary and analysis guide for the recorded data |

## How answers are produced

1. `app.js` scores `knowledge.json` entries (`selectKb`) and picks the most relevant
   official pages from `sources.json` (`selectSources`).
2. The question, selected knowledge entries, source list and recent conversation are
   sent to the Apps Script proxy.
3. The proxy extracts the official pages and asks the model to answer only from the
   curated entries and extracted content.
4. The reply is rendered with links to the official page(s). If it cannot be grounded,
   the UI shows an honest "not enough information" reply.

The model cannot add URLs: only links from the provided source list are rendered.
Distress or wellbeing questions also trigger a counselling-support card.

## Testing

There is no automated browser test suite wired into CI. Practical checks:

- `check_links.py` validates every source URL (see below).
- `checkWiring()` in Apps Script validates every reporting tab and header.
- `previewDailyReport()` in Apps Script returns today's report without emailing.

## Accuracy and sourcing

Every answer was checked against the live NCI page it cites. Where a page did not
support a specific claim, the claim was removed rather than kept:

- Fee figures are **not** stated. NCI does not publish a single fee table on its
  Postgraduate Fees page, so the assistant points to the individual course page
  instead of quoting an unverified number.
- Results are described as published on MyDetails, not emailed.
- The exams page refers to the **Mayor Square campus**, not "Spencer Dock".
- The study-room booking link in the previous draft was wrong and was replaced with
  the correct per-room booking route.
- Resit dates are attributed to the Academic Calendar, and the three kinds of
  deferral are distinguished.
- "Spencer Dock" is used only where the source page uses it, for the study rooms.

One honest limitation: this assistant is only as current as its knowledge base. The
`lastReviewed` date is shown in the footer so it is obvious when information was
last confirmed. Semester dates, exam blocks, fees and scholarships all change, so
students should still open the linked official page before making plans.

## Privacy

No personal data is collected, stored or displayed. Questions are scrubbed in the
browser and again in Apps Script, so student numbers, email addresses and passwords
are replaced before anything is stored. The assistant asks for no name, student
number or email. Records are anonymous: a random per-tab session id and a device
type (desktop/mobile/tablet). The satisfaction survey is anonymous and optional.

## Recording, reports and the survey

The proxy records anonymous usage into a Google Sheet and builds reports from it.
Every tab, its columns and how to analyse them are documented in
[`docs/REPORTING.md`](docs/REPORTING.md). In short:

- `Searches`, `Visits`, `Survey responses` are the raw records.
- `Daily report`, `Survey summary`, `Top questions`, `Dashboard` are derived reports.
- `Needs content` is the "what should we write next" list.

The site shows a short 4-question satisfaction survey (one question at a time, thumbs
up/down) once per browser session. There is no free-text field in the survey, so
nothing typed by a student is stored.

## Running locally

Because `app.js` fetches `knowledge.json`, open it over HTTP rather than by
double-clicking the file:

```sh
python3 -m http.server 8000
# then visit http://localhost:8000
```

## Deploying

Any static host works. For GitHub Pages: push to `main`, then in the repository
settings set Pages to deploy from the `main` branch. After changing `app.js` or
`style.css`, bump the `?v=` query on the `<link>`/`<script>` tags in `index.html` so
browsers pick up the new files.

## Not included

No build tooling and no automated browser tests in CI. Re-checking the knowledge base
against the live NCI site is a manual step, and it is the step that matters most.

## Checking the source links

`check_links.py` hits every URL referenced by the knowledge base — the primary
`link`, any additional `links`, and any bare URL that appears inside an answer.
Run it before committing any change to `knowledge.json`:

    python3 check_links.py knowledge.json --timeout 30

It reports four outcomes that matter:

| Result | Meaning |
| --- | --- |
| `OK` | Page loaded. |
| `BROKEN` | HTTP 404 or 410, or the host does not resolve. Needs a new source. |
| `UNREACHABLE` / `TIMEOUT` | Connection refused, DNS or timeout. Retried once before being reported. |
| `BLOCKED` | HTTP 401/403/429. Usually a bot filter, **not** evidence the page was removed. |

`ncisupporthub.ncirl.ie` returns 403 to automated requests, so its articles
always show as `BLOCKED`. Those pages are real; confirm changes to them by hand.
`.github/workflows/link-check.yml` runs `check_links.py` every Monday and on any
change to `knowledge.json`, and opens a `link-check` issue if a cited page dies.
